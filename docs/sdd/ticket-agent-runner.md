# Запуск Codex по тикету

**Статус:** уточнённый вариант на проверку готовности пользователем.

## Цель

Из карточки готового тикета запускать отдельный локальный запуск Codex в выбранном Git-проекте, видеть его состояние и результат в трекере и получать уведомление о завершении.

## Сценарий

1. Пользователь открывает готовый тикет и нажимает **«Взять в работу»**. Это действие означает, что тикет готов к запуску кодового агента.
2. Трекер проверяет обязательные данные тикета и создаёт запись запуска со статусом `Queued`. Повторный запрос не создаёт второй активный запуск.
3. Локальный worker на компьютере пользователя получает запуск, находит выбранный проект в заранее настроенном allowlist и создаёт отдельную Git-ветку/worktree.
4. Worker запускает Codex CLI с заголовком, описанием, критериями приёмки, ссылкой на спецификацию и инструкциями `AGENTS.md` проекта.
5. Worker передаёт события запуска в трекер. На странице тикета видны статус, краткий прогресс, ошибки и итоговый отчёт.
6. При успешном завершении тикет переводится в `Review`; ветка и worktree остаются доступны для последующего ревью. Worker не создаёт PR. Merge и deploy остаются за пользователем.
7. При ошибке или необходимости решения пользователя запуск получает соответствующий статус, тикет остаётся `In Progress`, а в трекере появляется постоянное уведомление. `Waiting for user` завершает текущую попытку; после разрешения вопроса и обновления тикета можно создать новый запуск, прежняя попытка остаётся в истории.

## Архитектура MVP

- Ticket Tracker остаётся веб-приложением FastAPI в Docker.
- Отдельный локальный worker запускается на хост-машине, где доступны Codex CLI, Git и локальные репозитории. Worker общается с трекером по локальному API.
- Codex запускается командой `codex exec --json`: процесс неинтерактивный, события можно передавать в UI. Используется сохранённая CLI-аутентификация пользователя; API key не встраивается в контейнер трекера.
- Для каждого запуска создаётся отдельная Git-ветка и worktree от настроенной базовой ветки. Существующая рабочая копия пользователя не меняется.
- Каталоги репозиториев задаются в локальной конфигурации worker по allowlist. Путь к произвольному каталогу из HTTP-запроса не принимается.
- Агент работает с ограниченными правами записи в worktree. Он не мержит PR и не выполняет deploy.
- Запуски и уведомления сохраняются в SQLite трекера, чтобы результат не терялся после перезапуска приложения или закрытия вкладки.
- Прогресс и итог доступны на странице тикета. Постоянное уведомление хранится в трекере; браузерное уведомление показывается, если вкладка открыта и разрешение выдано.
- Начальный allowlist включает локальные проекты `ticket-tracker` и `vacancy-search`; список и пути задаются конфигурацией worker.

## Данные запуска

Для каждого запуска трекер хранит как минимум: ticket ID, идентификатор проекта, статус (`Queued`, `Running`, `Waiting for user`, `Succeeded`, `Failed`), Codex run/thread ID при наличии, ветку/worktree, timestamps, краткий прогресс, итоговый отчёт, ошибку и URL PR.

История предыдущих запусков сохраняется. Одновременно для одного тикета допускается не более одного активного запуска (`Queued` или `Running`). `Succeeded`, `Failed` и `Waiting for user` — завершённые попытки; они остаются в истории и не блокируют новую.

## Критерии приёмки

1. Для готового тикета пользователь может вручную запустить работу агента; перед запуском показано подтверждение с названием тикета и целевым проектом.
2. Повторный клик или повторный HTTP-запрос при активном запуске не создаёт дубликат.
3. Перед созданием запуска валидируются обязательные поля и наличие настроенного проекта; при ошибке пользователь видит понятное сообщение, тикет не переводится в `In Progress`.
4. После успешного помещения в очередь тикет получает статус `In Progress`, а запуск — `Queued`.
5. Worker запускает Codex только в зарегистрированном проекте и отдельном worktree; исходная рабочая копия остаётся нетронутой.
6. В инструкции Codex передаются данные тикета и проектные инструкции. Запуск использует ограниченную политику доступа и не может выполнить merge или deploy.
7. В трекере сохраняются переходы состояния, сообщения о прогрессе, результат и ошибка. После перезагрузки страницы состояние остаётся доступным.
8. Успешный запуск переводит тикет в `Review`; имя ветки и итоговый отчёт показываются в тикете. PR автоматически не создаётся.
9. Ошибка запуска или ожидание пользовательского решения не теряются: статус и причина видны в тикете, пользователь получает постоянное уведомление. Завершённый запуск `Waiting for user` не блокирует новую попытку.
10. В трекере можно открыть итоговый отчёт и историю запусков по тикету.
11. Merge, deploy и перевод в `Done` не выполняются автоматически.

## Вне первой версии

- Запуск в облаке или удалённой машине.
- Несколько пользователей, роли и права доступа.
- Telegram/email уведомления; первый вариант — сохранённое уведомление внутри трекера.
- Автоматический merge, deploy и перевод в `Done`.
- Одновременное выполнение нескольких агентов в одном worktree.
- Поддержка произвольных shell-команд, проектов или пользовательских параметров из браузера.

## Согласованные решения

1. Прогресс и результат отображаются внутри трекера; отдельный чат Codex не входит в MVP.
2. Пользователь выбирает проект из локального allowlist.
3. Уведомление сохраняется в трекере; браузерное уведомление показывается при открытой вкладке и выданном разрешении. Telegram/email не входят в MVP.
4. Worker создаёт ветку/worktree, но не создаёт PR. Следующие шаги выполняются обычным согласованным процессом.
5. Для запуска нужны непустые описание, критерии приёмки, утверждённая спецификация и выбранный проект.

## Источники по способу интеграции

- OpenAI описывает `codex exec` как подход для ограниченного неинтерактивного запуска, SDK — для программной работы с сессиями, а app-server — для интеграции с постоянными диалогами, потоковыми событиями и обработкой approval. Для локального worker выбран `codex exec --json`: прогресс и результат отображаются в трекере, полноценная Codex-сессия в отдельном окне не требуется.
